# Аудит кода RAG-проекта

**Дата:** 22 июля 2026
**Объём:** ~80 модулей, ~26 800 строк Python + shell/CI/конфиги
**Метод:** сплошное чтение всех модулей шестью параллельными ревью-агентами (ядро RAG, ingest/данные, LLM-слой, боты/голос, admin/settings, инфраструктура), ключевые находки перепроверены по исходникам.

---

## Краткое резюме

Проект зрелый и «выстраданный»: широкая поддержка форматов, продуманные операционные детали (backpressure Qdrant, кооперативная отмена задач, деградации Redis→SQLite→память), аккуратные докстринги и защита от промпт-инъекций. Виден высокий уровень инженерной культуры «на бумаге».

Но есть три системных проблемы, которые перевешивают:

1. **Рефакторинг фасада `vectorstore` обогнал потребителей.** Три модуля — `calibrate.py`, `tg_train.py`, `org_index.py` — обращаются к `retriever._client` / `retriever._COLLECTION`, которых **больше не существует**. Это значит, что автокалибровка, обучение через Telegram и индексация оргсправочника **не работают в принципе** (падают с `AttributeError`), причём Telegram-загрузка при этом **молча удаляет присланные пользователем файлы**. Ловить это некому: на 26 800 строк приходится ~15 тестов.

2. **Безопасность держится на предположении «только доверенная LAN», которое дефолты не форсируют.** В репозиторий закоммичен рабочий админ-токен `secret123`; при пустом токене вся админка (~100 эндпоинтов, включая reinstall/reset/SSH-деплой/SSRF) открыта без аутентификации; CORS `*`; Qdrant и голосовой SIP-порт слушают `0.0.0.0` без пароля.

3. **Асинхронность «наполовину».** FastAPI-эндпоинты объявлены `async`, но весь горячий путь (эмбеддер, реранкер, синхронный httpx к Qdrant, до 3 вспомогательных LLM-вызовов, Whisper, учёт активности на каждый токен) исполняется прямо в event loop. Под конкурентной нагрузкой сервис фактически однопоточный.

Ниже — находки по важности. В каждой указаны файл:строка, сценарий отказа и рекомендация.

## CRITICAL

### C1. Мёртвый API `retriever._client` — не работают калибровка, TG-обучение и оргсправочник; файлы пользователей теряются
**Файлы:** `calibrate.py:139–144`, `tg_train.py:87,116–117`, `org_index.py:145,149,169`

`retriever.py` больше не определяет `_client` и `_COLLECTION` — работа с векторной БД вынесена в фасад `vectorstore`. Проверено: `grep "_client\|_COLLECTION" retriever.py` не находит ничего, а три модуля продолжают эти атрибуты вызывать.

- `calibrate.start()` → `_candidates()` падает `AttributeError` → калибровка всегда «Ошибка».
- `tg_train.save_and_index()` → `index_path()` падает, исключение перехватывается, `n=0`, и **присланный файл удаляется** (`tg_train.py:104–107`) — пользователь получает `{"chunks": 0}`, документ не проиндексирован и стёрт.
- `org_index.sync_index()` падает, ошибка глотается, `org_structure.sync()` возвращает `ok:True` — ассистент никогда не отвечает на «телефон Иванова», хотя справочник в БД обновляется (тихий отказ).
- Удаление точек (`_delete_by`) тоже молча не работает — «удалённые» чанки остаются в индексе и продолжают попадать в ответы.

**Рекомендация:** перевести все три модуля на фасад — `vectorstore.search/upsert/delete(...)`. Дополнительно в `calibrate.py` `retriever._build_filter()` возвращает «нейтральный» dict, а не `qdrant_client.models.Filter` — даже с живым клиентом фильтр был бы невалиден. Смок-тест на импорты и `hasattr` поймал бы всё это мгновенно (см. блок «Тесты»).

### C2. Закоммиченный админ-токен + открытая по умолчанию админка = удалённый RCE/уничтожение данных
**Файлы:** `runtime_config.json:139` (`"ADMIN_TOKEN": "secret123"`), `.env.example:63` (пусто), `app.py:207–210`, `app.py:72` (CORS `*`)

Вся аутентификация админки — `_check_admin`: `if current and token != current: raise 401`. При **пустом** `ADMIN_TOKEN` (дефолт в `.env.example`) проверка пропускает любой запрос. При этом в репозитории лежит готовый рабочий токен `secret123`, а API по умолчанию слушает `0.0.0.0:8000` с CORS `allow_origins=["*"]`.

Под неаутентифицированным доступом оказываются операции, эквивалентные RCE: `update_app()` (git reset --hard + pip install + os._exit), `reinstall_full()`, `reset()` (стирание индекса/настроек/журнала), `ingest_web` (SSRF во внутреннюю сеть), `browse()` (листинг любой директории), SSH-деплой на удалённые хосты.

**Сценарий:** сотрудник открывает вредоносную страницу → JS шлёт `POST http://rag-host:8000/api/admin/reset` (CORS `*` + пустой токен это разрешают) → база знаний уничтожена без единого пароля. Либо инсталляция с незаменённым `secret123` доступна из сети с известным паролем.

**Рекомендация:** fail-closed — отказ старта админ-роутов при незаданном токене, либо биндить их на `127.0.0.1`; убрать `secret123` из коммита и генерировать случайный токен при установке; сравнение через `hmac.compare_digest`; CORS ограничить списком доменов, для админ-путей отключить; проверка `Origin/Referer` на мутирующих запросах (anti-CSRF).

### C3. Стриминг LLM не проверяет статус ответа — тихий пустой ответ со статусом «успех»
**Файл:** `llm_backend.py:215–241` (openai), `llm_backend.py:252–272` (ollama)

В `chat_stream()` после открытия стрима нет ни `raise_for_status()`, ни разбора поля `error`. При 4xx/5xx тело не содержит строк `data:` — генератор отдаёт 0 токенов и `ok=True` уходит в аналитику. В ollama-ветке ошибка приходит как `{"error": "..."}`, но ключ `error` нигде не читается.

**Сценарий:** vLLM вернул 400 (превышен контекст) или Ollama — `{"error":"model not found"}`. Пользователь в чате/Telegram получает **пустой** ответ, дашборд показывает успешный вызов, алерты молчат, по логам невоспроизводимо.

**Рекомендация:** для стрима читать тело при статусе ≥400 и поднимать исключение; в ollama-ветке проверять `obj.get("error")`.

## HIGH

### H1. Синхронный горячий путь блокирует event loop — сервис фактически однопоточный
**Файлы:** `app.py:427,433,437,385` (`/chat`), `app.py:671–678` (`/chat-doc`), `app.py:743` (`/api/transcribe`), `llm_backend.py:236–282`

`async def chat` напрямую вызывает синхронный пайплайн: эмбеддинг (GPU/CPU), httpx к Qdrant, BM25, кросс-энкодер реранк, а при `SMART_FILTER`/`QUERY_REWRITE`/`DIALOG_REWRITE` — ещё 1–3 синхронных LLM-вызова. Всё в event loop. `/api/transcribe` блокирует loop на всё время Whisper (десятки секунд). Внутри `chat_stream` на каждые ~64 символа — синхронный Redis/SQLite-учёт активности. Показательно, что в `kag.py` те же вызовы аккуратно уведены в `asyncio.to_thread`, а в основном пути — нет.

**Сценарий:** два сотрудника задают вопрос одновременно; второй запрос (и стриминги, и `/health`) висят, пока первый не пройдёт retrieve+rerank+LLM. Один запрос на транскрибацию замораживает весь сервис.

**Рекомендация:** обернуть `search`, `standalone_question`, `no_answer_fallback`, `_embed_query`, разбор файла, транскрибацию в `asyncio.to_thread`/`run_in_executor`; учёт активности — батчить по времени (раз в 1–2 с), а не на каждый чанк.

### H2. Синглтоны моделей `@lru_cache` не сбрасываются при смене настроек → отравление кэша эмбеддингов
**Файл:** `retriever.py:22–29,164–186,230–235`

`_embedder()`/`_reranker()` кэшируются навсегда, но ключи Redis-кэша строятся из **текущих** настроек (`emb:sha1(EMBED_MODEL|вопрос)`). После смены `EMBED_MODEL` в админке без рестарта векторы считаются старой моделью, но сохраняются под именем новой — кэш отравлен и переживает рестарт (TTL сутки).

**Сценарий:** админ переключает модель и переиндексирует базу; до рестарта процесса все запросы ищут вектором старой модели по новой коллекции (несовпадение пространств → мусорная выдача), а «правильно» подписанный кэш продолжает отдавать мусор ещё до суток после рестарта.

**Рекомендация:** ключевать `lru_cache` параметрами (`_embedder(model, device)`) либо `cache_clear()` + `cache.bump('embed')` из `settings.update`.

### H3. Последовательный ingest удаляет старые векторы ДО парсинга → документ исчезает при сбое
**Файл:** `ingest.py:574` против корректного `ingest.py:538` (`_consume`)

В однопоточном режиме `delete_old_versions(source)` вызывается до `load_file()`. Если парсинг упал, попал под `FILE_PARSE_TIMEOUT` (который как раз форсирует `workers=1`) или дал 0 чанков — старые точки уже удалены, новые не записаны. В параллельном пути удаление корректно перенесено после парсинга — две копии одной логики разошлись.

**Сценарий:** тяжёлый PDF, ранее индексировавшийся за 40 с, упирается в лимит 30 с → документ полностью исчезает из поиска до ручного вмешательства.

**Рекомендация:** удалять старые версии только после успешного парсинга; в идеале — upsert по детерминированным ID (`uuid5` от `source+chunk_idx`), тогда «дыры» между delete и upsert исчезают вовсе.

### H4. Текстовые форматы читаются без определения кодировки → cp1251-файлы теряют кириллицу
**Файл:** `loaders.py:78` (.txt/.md), `353` (.html), `1059` (.json), `1082` (.url) и др.

Везде `read_text(errors="ignore")` без явной кодировки. Байты cp1251 (Windows/1С-выгрузки) невалидны в UTF-8 и с `errors="ignore"` просто выбрасываются. При этом для CSV написан аккуратный детектор `_read_csv_any` (charset_normalizer + cp1251-фолбэк) — для txt/html его забыли применить.

**Сценарий:** русскоязычный `инструкция.txt` в cp1251 индексируется почти пустым, попадает в `n_skip` как «пустой», никто не замечает.

**Рекомендация:** вынести декодирование из `_read_csv_any` в общий `_read_text_any(path)` и использовать во всех текстовых загрузчиках.

### H5. Утечка слота LLM-очереди при отмене запроса во время ожидания
**Файл:** `llm_backend.py:196` + `llm_queue.py:318–366`

`await run_in_executor(None, llm_queue.acquire)` — если клиент закрыл соединение, пока запрос стоял в очереди, `CancelledError` прилетает в корутину, но поток в executor уже занял слот, а `release()` не вызывается (отмена до входа в `try`). Токен не возвращается.

**Сценарий:** `LLM_MAX_CONCURRENCY=1`, два нетерпеливых пользователя обновили страницу → два осиротевших слота. `_prune_dead` не спасёт (процесс жив), очередь встаёт до `_HOLD_TTL=30 мин`.

**Рекомендация:** компенсирующий `release` через callback на future executor'а, либо асинхронная реализация acquire.

### H6. Не-стриминговый `chat()` падает по read-timeout на длинных генерациях
**Файл:** `llm_backend.py:300,313,23–31`

Логика «read-timeout сбрасывается на каждом токене» верна только для стрима. При `stream=False` сервер молчит до конца генерации, поэтому read-timeout (180 с) — жёсткий лимит на весь ответ. С `LLM_THINK=True` (дефолт) любой служебный вызов через `chat()` (intent, калибровка, enrich) длиннее 3 минут стабильно падает при живом бэкенде, а генерация на GPU продолжается впустую.

**Рекомендация:** отдельный увеличенный таймаут для не-стриминговых вызовов (или `read=None` + общий cap).

### H7. Обход лимита конкурентности при сбое общего хранилища очереди
**Файл:** `llm_queue.py:281–315` (`_try_acquire`)

Если Redis- или SQLite-ветка бросает исключение (для SQLite `database is locked` при конкуренции — ожидаемо), код молча проваливается в проверку по локальному `_local_active` этого процесса, который пуст → запрос проходит мимо лимита. Ровно тот эффект «выполняется 3/1», от которого защищались.

**Сценарий:** web-процесс и `ingest` конкурируют за SQLite; vision-вызовы ingest идут мимо лимита, GPU перегружается, чаты падают по таймауту.

**Рекомендация:** при сбое общего уровня трактовать как «слот не получен» (retry), а не проваливаться в локальный; для SQLite — ретраить `BEGIN IMMEDIATE`.

### H8. Голосовой SIP-порт открыт всей сети без аутентификации
**Файл:** `sip_bridge.py:355–378,392–393`

AudioSocket-сервер по умолчанию биндится на `0.0.0.0:8090`: UUID из кадра `KIND_ID` не проверяется, нет allowlist по IP, нет лимита соединений (поток на каждый accept). Любой хост с сетевым доступом получает полный голосовой интерфейс к корпоративной базе (STT→RAG→TTS) и может поднять неограниченное число «звонков», каждый из которых грузит Whisper/LLM/TTS.

**Рекомендация:** дефолт `127.0.0.1`, проверка UUID/секрета из диалплана, лимит активных сессий, allowlist адресов АТС.

### H9. Telegram: рестарт бота молча убивает поллер; все запросы обрабатываются последовательно
**Файл:** `telegram_bot.py:948–976` (restart), `905–936` (`_loop`)

(а) `restart()` = `stop()` → `sleep(0.6)` → `start()`, но поток поллера в этот момент заблокирован в long-poll `getUpdates` (таймаут 40 с). `start()` видит живой поток, возвращает «уже запущен» и не очищает `_stop`; когда long-poll вернётся, старый поток видит `_stop` и завершается — бот мёртв, статус показывает «запущен». (б) Все апдейты всех пользователей идут строго последовательно в одном потоке: один тяжёлый запрос (OCR, длинная генерация, XTTS до 180 с) блокирует ответы всем.

**Рекомендация:** в `restart()` — `join(timeout=45)` или generation-id потока; пул воркеров с сериализацией по `chat_id` и глобальным семафором на LLM, поллер только диспетчеризует.

### H10. SSRF/инъекция параметров во внешние API-хуки
**Файл:** `api_tools.py:103–108` (`_fill` — сырой `str.replace`), `128–153`, `140` (`follow_redirects=True`)

`{q}` (весь вопрос пользователя) и `{param}` (regex-группы из вопроса) подставляются в URL и тело без URL-кодирования и валидации. Пользователь чата управляет частью URL (может дописать `&token=`, сменить путь через `/../`), а `follow_redirects=True` позволяет целевому серверу перенаправить запрос с заголовками на внутренний адрес. В связке с закоммиченным токеном и `dns_override` — путь к внутренней сети.

**Рекомендация:** `urllib.parse.quote()` для URL-подстановок, `json.dumps` для JSON-тела, запрет редиректов или allowlist хостов/схем.

### H11. Уязвимый torch 2.5.1 (CVE-2025-32434, RCE через torch.load) + непиненный transformers
**Файл:** `requirements.txt:17` (`torch==2.5.1`), `44` (`mlx-whisper`), отсутствие пина `transformers`

`torch==2.5.1` уязвим к RCE через `torch.load` даже с `weights_only=True` (исправлено в 2.6.0). Админка позволяет менять `EMBED_MODEL`/`RERANK_MODEL` на произвольный HF-тег → загрузка недоверенного чекпойнта = выполнение кода на сервере с корпоративными документами. Отдельно: `transformers` не запинен, хотя `setup.sh:111` прямо утверждает, что ядро требует `transformers==4.44.2` (из-за чего XTTS изолирован в отдельный venv) — на свежей установке приедет другая версия, скоры реранка «поплывут» между серверами. `Pillow 11.0.0` (парсит недоверенные картинки для OCR) — ниже патчей 11.3.x, устранявших heap-overflow.

**Рекомендация:** поднять torch≥2.6 (проверив совместимость с sentence-transformers 3.3.1 / FlagEmbedding 1.3.3), запинить transformers, обновить Pillow; `mlx-whisper` — под platform marker `; sys_platform == "darwin"`.

### H12. Qdrant опубликован на всех интерфейсах без пароля
**Файл:** `docker-compose.yml:6–8` (`"6333:6333"`, `"6334:6334"`)

Qdrant без API-ключа не аутентифицирует запросы. При внешнем IP любой может `curl -X DELETE http://host:6333/collections/company_kb`. PMI-документ (`gen_pmi.py:459`) заявляет «внешние службы только в приватной сети» — compose это сам нарушает.

**Рекомендация:** `"127.0.0.1:6333:6333"`, убрать 6334 если gRPC не используется, либо задать `QDRANT__SERVICE__API_KEY` и прописать клиенту.

### H13. `reinstall_server.sh` необратимо стирает данные по кнопке в админке без бэкапа
**Файл:** `reinstall_server.sh:16–19,26–30`

`rm -rf .venv graph_storage runtime_config.json rag_logs.db qdrant_storage ...` с обходом подтверждения через `CONFIRM=yes` («используется из админки»). Бэкап перед стиранием не создаётся, хотя `backup.py` в проекте есть.

**Рекомендация:** автоматический вызов `backup.py` перед `rm -rf`; в админ-эндпоинте — повторный ввод токена/двойное подтверждение.

### H14. LLM-автокалибровка мутирует живые прод-настройки без отката
**Файл:** `calibrate.py:1481–1533,1349–1363`; аналогично `admin_ops.py:2740–2744` (`retrieval_autotune`) и `admin_ops.py` autotune

Итеративная калибровка на каждой итерации меняет глобальные `settings.update(MIN_SCORE, TEMPERATURE, ENGINE, ...)`. Исходные значения не сохраняются; лучшие применяются только при нормальном завершении. При отмене или исключении система остаётся с последними экспериментальными параметрами от LLM. Всё время перебора **реальные пользователи получают ответы на экспериментальных настройках**.

**Рекомендация:** снапшот настроек до цикла + восстановление в `finally`; в идеале — оценивать параметры через per-request override, не трогая глобальный `_state`.

## MEDIUM

### Ядро RAG
- **M1. ## Общая оценка

Сильные стороны реальны: широкая функциональность, внимание к операционным граблям, читаемый код с осмысленными комментариями. Слабости — не в отдельных строчках, а в двух системных паттернах. Первый — **культ `except Exception: pass`**: десятки мест, где инфраструктурная ошибка (delete в Qdrant, итератор Milvus, verify, индексация, org_index) молча превращается в тихую потерю данных или неверную статистику. Ошибки надо делить на «деградация допустима» и «функция сломана — сигнализировать в статус/метрику». Второй — **состояние и рефакторинг без страховки**: синглтоны не согласованы с горячей сменой настроек и много-loop реальностью, фоновые задачи мутируют живые прод-настройки, а отсутствие тестов превращает любое переименование в «толстых» модулях в лотерею — что уже материализовалось в C1.

Наибольшую отдачу даст не рефакторинг ради красоты, а четыре дешёвых хода: починить `retriever._client`, сделать безопасность fail-closed по умолчанию, увести синхронный пайплайн из event loop и добавить смок-тесты импортов. Это одновременно возвращает неработающие фичи, закрывает самый острый риск и превращает будущие рефакторинги из лотереи в рутину.
